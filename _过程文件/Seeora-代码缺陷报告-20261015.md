## 二、分级缺陷清单

### 【C-1】Critical · currentStreak 在漏签场景下归零 / 不延续（与产品核心承诺直接矛盾）

- **文件:行**：`native/src/lib/habitLogic.ts:210-229`（实现）、`native/src/lib/habitLogic.ts:204-209`（规范注释）、`native/src/lib/__tests__/habitLogic.test.ts:187-229`（测试）、`native/src/components/HabitRow.tsx:38,88`（界面呈现）
- **触发条件 / 复现**：习惯 `createdAt=2026-09-01`、`frequency=1`（默认），连续打卡 10 天（09-01…09-10），随后漏签。

  | 场景（now） | 期望（规格） | 实际（代码） |
  | --- | --- | --- |
  | 09-11 漏 1 天 | 仍是 10 | **10** ✅ |
  | 09-12 再漏 1 天（暂停） | 仍是 10 | **10** ✅ |
  | 09-13（第 3 天未打卡） | 仍是 10（不归零） | **0** ❌ |
  | 09-13 恢复打卡 | **11**（暂停点 +1） | **1** ❌ |

  规格原文（`habitLogic.ts:204-209`、`参考/07-习惯算法规格.md`）：「漏签第 1 天计数不变；连续漏签第 2 天 → 暂停，**直接停止**；**恢复打卡后从暂停点继续计数（不归零）**」，并给出示例「连打 10 天 → 漏 1 天(10) → 漏 1 天(10) → 打卡(变 11)」。
- **实际 vs 期望（代码层推演）**：`currentStreak` 从 `i = cur-1` 向前遍历（`habitLogic.ts:218`），只维护一个 `miss` 计数，`miss >= 2` 即 `break`（`:225`）。
  - 「暂停」被实现为「就地终止遍历」，**没有保存暂停前的累计值**（变量只有 `streak`，遇 `break` 时可能仍为 0）。
  - 当尾部连续漏签 ≥ 2（如 09-13 时向前遇到 09-12、09-11 两个 miss，中途没有 done）→ 直接 `break`，`streak` 停在 0 → **返回 0**。
  - 恢复打卡时（09-13 打卡），今日节点计 1，随后向前遇到 09-12、09-11 两个 miss → `break`，**永远回不到更早的 10 天** → 返回 1。
- **影响**：`HabitRow.tsx:88` 直接渲染 `d.curStreak · {streak}`（=`currentStreak`），即 Today 卡片「当前连续」会显示为 **0 或 1**。这与产品的头号卖点「漏签不会清零连续记录 / nothing ever resets to zero」（onboarding 文案）**正面冲突**，是本 App 最核心的信任资产，属于上线前最严重的体验/信任事故。同时该错值还会传入 `toggleToday` 的 `streak/newBest` 与撒花判定（`useHabitActions.ts:127-153`），连带影响「新纪录」语义。
- **修复建议**：让 `currentStreak` 落地规格语义。两种可行改法（择一）：
  1. 变量法：保留 `miss` 语义，但 **在 `break` 之前把已累计的 `streak` 记住**，恢复打卡时以「暂停值 + 后续连续」计算；即把 `miss>=2` 从「终止遍历」改为「标记暂停后继续向前累计并冻结」。
  2. 简洁法：向前遍历**不因 2 连漏而 break**，而是把「连续漏 2」视为一次「间隔」（gap）处理：遇到一次长度为 2 的漏签段只标记一次暂停，累计值保留；恢复后继续 +1。
  - 同步**修正测试**：`habitLogic.test.ts:204-209` 目前把错误行为断言为正确（见第五节），必须改为断言「09-13 打卡返回 11、09-13 未打卡返回 10」。

### 【M-1】Major · 生产构建缺少 ErrorBoundary，渲染期异常直接白屏/红屏

- **文件:行**：`native/src/app/_layout.tsx:58-82`（尤见 `:77-81`）
- **触发条件**：生产构建（`EXPO_PUBLIC_TM_SURFACE` 未设 → `SURFACE=false`）下，任意页面在渲染期抛出 JS 异常（数据驱动视图、`Svg` 绘制、长列表等）。
- **实际 vs 期望**：代码仅在**诊断构建**才包裹 `DiagnosticErrorBoundary`（`:78`），生产分支 `return tree`（`:80`）——**没有任何全局错误边界**。期望：生产至少有一个轻量 ErrorBoundary 兜底（可渲染「出错」页 + 引导），而非整屏失效。
- **影响**：本项目历史上存在 iOS 26 + Fabric 冷启动/渲染崩溃族（见 `_layout.tsx:96-101` 注释），生产一旦命中渲染异常将直接白屏，用户无法自救；虽本地数据已落盘，但体验为「应用坏了」。
- **修复建议**：生产分支挂一个最小 ErrorBoundary（复用 `DiagnosticErrorBoundary` 的容错逻辑但去掉诊断浮层），或至少在根层用 `React.ErrorBoundary` 语义组件兜底。

### 【M-4】Major · 本地持久化 fire-and-forget + 静默吞错（数据安全 / 本地唯一副本）

- **文件:行**：`native/src/store/usePersist.ts:30-32`（`persist` = `void sset(...)`，不 await）、`:33-43`（`snapshotNow` 以闭包状态组装）、`native/src/lib/storage.ts:35-41`（`sset` → `try { await setItem } catch { /* 静默降级 */ }`）
- **触发条件**：① 快速连续写（连续勾选多个习惯、编辑后立刻打卡）；② AsyncStorage 写入失败（磁盘满/被杀进程）。
- **实际 vs 期望**：每次变更都调用 `persist(snapshotNow(...))`（如 `useHabitActions.ts:86,266,292,485` 等），但**既不 await、也无串行队列/版本号**——异步写盘不保证落盘顺序，理论上「较新快照先完成、较旧快照后完成」会把最新状态覆盖回旧值；且 `sset` 捕获异常后**对用户完全不可见**（无 toast/日志）。期望：关键状态写入串行化并至少对失败有可见反馈。本 App **无云端备份、本地是唯一数据副本**，静默丢失代价高。
- **影响**：极端情况下丢最新一次变更；持久化失败时用户毫无感知。属数据安全类 Major（概率低、影响高）。
- **修复建议**：为 `persist` 增加一个「最后写入者胜」的串行队列（`Promise` 链）或写入序号校验；`sset` 失败至少 `console.warn` 一次并在关键路径（如批量导入后）向用户提示。

## 三、对 10-14 旧结论的独立复核

### 1) Critical：`currentStreak` 归零 —— **成立，且比旧结论更精确**

**判断依据**：`habitLogic.ts:210-229` 的实现只用一个 `miss` 计数器并在 `miss>=2` 时 `break`，**未保存暂停点累计值**；同一文件 `:204-209` 的规范注释与 `参考/07-习惯算法规格.md` 明确要求「恢复打卡后从暂停点继续计数（不归零）」，且给出「……漏 1 天(10) → 漏 1 天(10) → 打卡(变 11)」的示例。代码推演得到两个反例：
- 第 3 天连续漏签 → 返回 **0**（应保持暂停值）；
- 中断 ≥2 天后恢复打卡 → 返回 **1**（应为暂停值 +1，例中应为 11）。

故「归零问题」属实。需补充的是：旧结论只提「归零」，实际还有「**恢复后不延续**（回落到 1）」这一同等严重的表现，二者同源。

### 2) Major：`saveHabit` 免费额度可被绕过 —— **不成立（误报）**

**判断依据**（逐入口排查）：
- 新建入口：`useHabitActions.ts:278-285`，`!pro && habits.length >= FREE_HABIT_LIMIT` 时**先关表单再 `openPro("habitLimit")` 并 `return`**，第 6 条无法经表单建立；`openHabitForm`（`:211-232`）本身不校验但仅跳转表单，最终仍由 `saveHabit` 收口，前后一致。
- 兜底冻结：`store/app.tsx:246-251`，`pro=false` 时按 `createdAt` 升序只保留最早 `FREE_HABIT_LIMIT` 个可用，其余冻结；`blockIfFrozen`（`:100-105`）拦截打卡/休息/补签/编辑四类写操作。
- 归档不释放额度：`useHabitActions.ts:358-362` 注释与 `frozenIds` 逻辑一致（统计**全部**习惯含归档），堵死「归档→新建→再归档」循环。
- 导入路径：`importBackup`（`:448-487`）**确实没有**做 `FREE_HABIT_LIMIT` 校验——这是唯一真实存在的缺口。**但导入只能经 `/settings` 的导出/导入弹层触发，而 `openExport` 已被 `gatePro("dataExport")` 门禁**（`store/app.tsx:391-394` + `usePro.ts:165-172`：非 Pro 直接 toast + 跳买断页并 `return false`）。因此**免费（试用结束且未买断）用户不可达导入**。

**结论**：对「免费用户可绕过 5 条上限获得 >5 条**可操作**习惯」——**不成立**。残余的软性缺口有三，均非功能性绕过：① 试用期内 `pro=true`（`app.tsx:203`）可无限新建/导入，试用结束仅冻结、仅留 5 条可操作；② 改系统时间可让 `trialUntil`（本地计时）延长；③ 导入无额度校验（但被 Pro 门禁挡住）。建议顺手在 `importBackup` 入口补一句额度提示（可选，非必须）。

### 3) ~42 个 Minor —— **方向成立，数量未能复现**

**判断依据**：独立盘点得 Minor 14 条（见上表），主体集中在「未使用导出/死代码、调试日志、i18n 绕过、输入校验、a11y、启动期原生模块、副作用不纯」类别，与 10-14 结论的定性一致；但我**未复现 42 这个精确数字**，也未逐条枚举旧清单（该摘要未落盘、无原始条目可对齐）。可确认的是：本轮 Minor 中 `m-1/m-3/m-4/m-11` 与旧结论「未使用导出 / 调试代码 / a11y 缺失」的描述相符，说明旧结论方向正确、颗粒度偏粗。

## 四、明确排除（非缺陷）

以下项经证据核查**不构成缺陷**，特此排除以防误判：

1. **日期 / 时区错一天**：`dates.ts:9-15` `fmtDate/todayStr` 全部取**本地**年月日；`createdAt` 用 `todayStr()`（`useHabitActions.ts:289`，注释 `:286-288` 说明 C-04 变体已修）；`habitStartDate`（`habitLogic.ts:130-136`）对「纯日期串」直接切串、对 ISO 串走本地解析。**不存在跨时区偏一天**。`updatedAt` 用 `toISOString`（见 m-13）仅元数据、无消费方。
2. **IAP 异常处理**：`withTimeout` 8s 硬超时（`iap.ts:33-44`）；**用户取消 ≠ 失败**（`usePro.ts:112-118`，取消静默）；恢复购买分级 `none/error/timeout/unconfigured` 且「没买过」用中性色而非报错（`usePro.ts:137-161`）；价格 `loading/ok/unavailable` 三态 + 可见原因 + 重试出路，`ready` 必定归位（`pro.tsx:49-59,76,267-284`）。**异常处理健壮**。
3. **i18n 中英键完整性与一致性**：`i18n.test.ts:24-87` 守卫「键集一一对应、无空串、插值占位符两侧一致、禁用订阅术语、`proTrialNote` 必须写明不会自动扣费」；抽查未发现缺键/占位符缺失。**未见缺键**。
4. **隐私 / 合规（上传、埋点、IDFA、自定义 userID、外部支付入口、硬编码价格）**：全库检索 `fetch/XMLHttpRequest/analytics/track/IDFA/AdvertisingId/userID/logIn` → **除 RC SDK 自身外 0 命中**；`app.json` 无 `NSUserTrackingUsageDescription`、权限仅 `INTERNET`（Android）与 `mailto` 查询白名单；源码内**无任何具体价格**（`iap.ts:5` 明示「代码中不出现任何具体价格」，价格运行时取 `priceString`，`pro.tsx:58`）；**无外部支付入口**（支付方式仅 App Store，`pro.tsx:286-291`）。`eas.json:37` 的 Apple ID 邮箱见 m-14。
5. **`any` 滥用**：全库 `as any/: any/any[]` 仅出现在 `iap.ts`（动态 import RevenueCat SDK 的边界），且带 `eslint-disable` 与成因说明（`iap.ts:46-47` 等）。属**合理必要**，非缺陷。
6. **购买状态仅信本地凭证**：hydration 直接信任 `SK.receipt {pro:true}`（`usePersist.ts:90,107`），但每次触碰付费入口都会 `syncEntitlement()` 与苹果侧核对、`inactive` 时降级（`usePro.ts:73-90`、`iap.ts:242-256`）。残余窗口（同步异步完成前的单次操作）极小，且 iOS 非越狱不可改写 AsyncStorage。**判定可接受**。
7. **诊断组件（`TurboModuleErrorSurface`/`DiagProbe`/`DiagnosticErrorBoundary`）**：仅当 `EXPO_PUBLIC_TM_SURFACE=1`/`DIAG=1` 时挂载，生产构建被摇树剔除（`_layout.tsx:32-37,69-70,77-81`）。**设计如此，但见 M-1（生产缺边界）。**
